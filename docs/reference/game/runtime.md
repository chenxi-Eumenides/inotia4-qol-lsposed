# 运行时、逻辑帧与线程模型

> 日期：2026-11-10 ｜ 适用版本：`c18-v520` / `c18-v603`（地址按版本核对）
> 来源：运行时确认 + `libgame.so` 符号/反汇编。本文只记录原版游戏的运行时事实，不描述模块或插件实现。

## 1. 线程模型

- 游戏是**单线程主循环**：逻辑推进、AI、状态/冷却计时、UI、存档读写都在同一主线程串行执行。
- 玩法逻辑不创建 worker 线程，也不使用 `sleep` 或定时器轮询；每帧比较时间戳推进状态。
- 外部程序若需调用游戏函数，必须在主线程执行；后台线程只能读取已经发布好的只读快照或原子标量，不能直接碰游戏内存或调用游戏函数。

## 2. 逻辑帧

- 逻辑帧固定 **60ms/帧**（约 16.7 FPS）。这是运行时事实，不是 60 FPS 的估算。
- 全局逻辑帧计数 `g_nGlobalCoolTimeCount`（`0x3099b0`，`.data`，8 字节）在 `GAMESTATE_ProcessPlay`（`0x9cba0`）每帧 `+1`，同时作为冷却等系统的“当前时间”。
- 冷却、Buff、药水等常量单位都是 tick；换算秒数必须用 **60ms/tick**：
  - `165 tick ≈ 9.9s`（药水冷却）
  - `15 tick ≈ 0.9s`（Buff 类道具冷却）
  - `45 tick ≈ 2.7s`
- 不要按 60 FPS（16.7ms/tick）换算；旧文档中的 60 FPS 示例已过期。

## 3. 主循环入口与帧锚点

| 位置 | 地址/符号 | 语义 |
|---|---|---|
| `GAMESTATE_ProcessPlay` | `0x9cba0` | 逻辑帧处理；递增全局 tick |
| `MainProcess` | 导出符号 | 游戏主循环；`+0x40` 为逻辑帧前置锚点 |
| `GAMESTATE_DrawPlay` | 导出符号 | 绘制处理；`+0x20` 为渲染前置锚点 |
| 帧计数 | `G_FRAME_COUNT_VMA`（经 GOT 读取 u64） | 当前帧号；`<= 0` 表示帧源尚未就绪 |

- 两个前置锚点分别位于“游戏逻辑之前”和“绘制之前”，适合插入每帧一次的工作。
- 插入点必须短小，禁止睡眠、阻塞等待或长时间占用主线程。
- 地址和偏移随游戏版本变化；使用前按符号名重新解析，不要硬编码跨版本地址。

## 4. 运行时状态机

| 状态 | 含义 | 观察 |
|---|---|---|
| `4` | 主菜单 | 存档槽区刷新只在主菜单发生 |
| `5` | 世界/进档完成 | 角色、地图、背包等运行时数据在世界状态可读 |

- 读档链：主菜单 → 选择槽 → 世界加载 → 状态 `5`。
- 进入世界前，角色对象和地图数据可能尚未完成挂接；此时读取角色/地图字段可能为空或旧值。
- 退出世界后回到主菜单状态，存档槽区才重新刷新。

## 5. 对逆向与外部程序的约束

1. 任何游戏读写/调用都必须在主线程；跨线程只能走只读快照。
2. 每帧工作按 60ms 预算分配；不要假设更高帧率或更短帧。
3. tick 与秒的换算固定使用 60ms/tick。
4. 帧号未就绪（`<= 0`）时不要派发依赖帧序号的工作。
5. 逻辑帧与渲染帧的锚点不同；不要把渲染前的工作放到逻辑前，或反之。
